# rs-spi 与 Rust 生态相关方案的比较

简体中文

## 范围与版本

本文以 `qubit-spi` 0.13.0 为基线，比较它与 Rust 中若干相关设计模式和库的职责、优势与取舍。这里的比较针对能力范围和集成模型，不代表基准测试结果，也不表示这些方案可以互换。外部项目的 API 和支持范围可能随版本变化；请以各项目的当前文档为准。

## 项目定位

`qubit-spi` 为静态链接的 Rust 应用提供类型化的服务提供者注册与解析机制。应用注册候选 provider，按名称、显式链或自动排序选择候选，再按配置调用工厂创建服务。它将候选选择与创建失败后的回退策略分开，并为同步和异步服务提供相应 API。

它适合多个可选后端由应用配置、而依赖库只需要面向服务抽象的场景。若只有一个实现且无需运行时选择，直接通过构造函数或 trait 注入通常更简单。

本 crate 不负责加载或卸载动态库、不建立通用依赖注入图、不缓存创建后的服务，也不监控已创建服务的健康状况或处理其后续运行故障。启用可选 `inventory` feature 可从最终二进制中已链接的静态条目发现 provider；这仍是链接期发现，不是运行时二进制插件加载。

## 工作模型

解析过程可概括为三个阶段：

1. **注册或发现**：应用显式注册 `ProviderDefinition`；也可以启用 `inventory` feature 收集已链接的静态 provider。
2. **选择**：`ProviderSelection` 按名称、链或自动顺序确定候选。自动顺序为优先级降序，再按规范 ID 升序。
3. **创建与回退**：resolver 按候选顺序调用工厂，并依据 `Never`、`OnAbsence` 或 `OnAnyError` 决定创建失败后是否继续。

`ServiceSpec` 将配置和领域错误类型绑定到服务族；同步或异步 capability trait 再绑定输出类型。目录克隆共享同一注册状态；解析结果持有候选快照，因此之后的目录变更不会改变已有 resolver 的候选集合。注册表锁不覆盖 provider 工厂调用或异步 future 的执行。

失败类别包括 `Unsupported`、`Unavailable`、`InvalidConfiguration` 和 `InitializationFailed`。回退行为取决于 provider 是否准确选择失败类别；本 crate 不会自动判断某个领域错误是否适合回退。异步创建被取消时，当前 future 会被丢弃，不会继续尝试下一个 provider，也不保证回滚已经发生的外部副作用。

## 方案比较

| 方案 | 优势 | 取舍 | 适用场景 |
| --- | --- | --- | --- |
| 直接 trait、构造函数或参数注入 | 依赖关系直接可见；无需注册表或发现机制；通常是最小的抽象和运行时开销。 | 多实现选择、回退和错误聚合需要调用方自行组织。 | 单一实现，或调用方本就掌握具体实现的场景。 |
| `qubit-spi` | 提供类型化 provider 目录、候选选择、创建策略和诊断；同步与异步 API 采用对应的模型。 | 需要定义服务族和注册流程；配置、错误模型在服务族内共享；不包含缓存、通用依赖图或动态库生命周期管理。 | 应用运行时需要在多个静态链接后端之间选择，并明确定义创建失败语义。 |
| [`inventory`](https://docs.rs/inventory/latest/inventory/) | 支持从不同 crate 提交静态条目，由最终程序收集；适用于分散定义的注册声明。 | 主要解决条目收集，不规定 provider 的选择、创建、回退或错误协议；迭代顺序不保证。依赖 crate 也必须实际进入最终链接产物。 | 需要静态分布式注册，并由应用或另一层决定后续处理的场景。 |
| [`linkme`](https://docs.rs/linkme/latest/linkme/) | 通过 distributed slice 汇集静态元素，使用方读取切片；适合构建期确定的表。 | 元素需满足静态初始化等约束；它本身不定义服务构造、选择策略或失败处理。 | 命令表、处理器表或其他构建期固定的静态集合。 |
| [`shaku`](https://docs.rs/shaku/latest/shaku/) | 面向依赖注入和组件组合，可描述应用模块中的组件及依赖。 | 关注对象依赖图和注入；若需求只是多个后端间的选择与创建回退，其抽象范围可能更大。 | 应用希望以依赖注入方式组织一组相互依赖的组件。 |
| [`abi_stable`](https://docs.rs/abi_stable/latest/abi_stable/) | 面向 Rust 库间的稳定 ABI 和运行时加载，可用于需要跨动态库边界的扩展系统。 | 需要遵循 FFI-safe 类型和稳定 ABI 约束，并处理加载、兼容性及资源生命周期；不等同于普通 Rust trait 注册。 | 插件以独立动态库交付、宿主需在运行时加载的场景。 |

这些方案可以组合。例如，`inventory` 可作为静态 provider 的发现来源，之后由 `qubit-spi` 执行目录校验、选择和创建。选择哪种方案应由部署边界和所需语义决定，而不是仅按 API 数量或性能印象判断。本文不声称存在跨方案的性能优劣；性能敏感场景应在目标工作负载和平台上测量。

## 采用建议与限制

- 若只需一个实现，或调用点可以显式传入实现，优先考虑直接依赖注入。
- 若需要在多个静态链接后端之间按配置选择，并对创建失败采用明确回退策略，可考虑 `qubit-spi`。
- 若 provider 分散在多个静态扩展 crate，可将 `inventory` 用作发现层；仍需确保相关 crate 被链接，并在应用中构建目录。
- 若需要加载独立发布的二进制插件，应选择并单独设计稳定 ABI 插件边界；`qubit-spi` 可作为宿主进程内的后端选择层，但不能代替该边界。

采用 `qubit-spi` 时还需考虑：一个服务族共享一套配置和领域错误类型；异步接口使用 boxed `Send` future，不适合要求 `!Send` future 的场景；回退是否正确依赖 provider 对错误类别的准确映射；注册表的作用域与封存时机由应用决定。项目包含 benchmark，但本文未运行跨方案对比，因此不据此作性能结论。
