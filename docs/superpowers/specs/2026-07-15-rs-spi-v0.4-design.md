# rs-spi 0.4 Design

**Status:** Accepted for planning  
**Date:** 2026-07-15  
**Scope:** `qubit-spi`, `qubit-fs`, `qubit-mime`, and `qubit-magika`; assembly guidance for `rs-platform` and `rs-llmsdk-core`

## Context

`qubit-spi` currently provides a typed, synchronous provider registry with
explicit registration, provider aliases, deterministic automatic selection,
fallback chains, availability checks, and service creation through `Box`,
`Arc`, or `Rc` handles.

The implementation is correct and well tested, but its public API and internal
structure mix six concerns:

1. provider identity and aliases;
2. provider metadata;
3. mutable registration and index maintenance;
4. provider selection and fallback policy;
5. service ownership conversion;
6. registration-time and resolution-time error aggregation.

This produces a matrix of named, automatic, and configured selection methods
for each supported handle type. Downstream crates repeat that matrix and add
mutable process-wide default registries.

The known consumers establish the actual design boundary:

- `qubit-fs` creates shared filesystem trait objects selected from URI-related
  configuration;
- `qubit-mime` has two independent SPI domains, MIME detectors and media stream
  classifiers, and exposes both boxed and shared creation methods;
- `qubit-magika` contributes an external MIME detector provider;
- `rs-platform` is the intended composition boundary but does not yet consume
  `qubit-spi` directly;
- `rs-llmsdk-core` intentionally uses provider-neutral dependency injection and
  must not gain a dependency on `qubit-spi`.

The registry is explicitly assembled during application startup. Runtime
registration, replacement, unloading, and hot reload are not requirements.

## Goals

- Make startup assembly explicit and runtime behavior immutable.
- Reduce the provider contract to one creation operation.
- Let each service specification own its complete output handle type.
- Separate registration errors, provider errors, and resolution errors.
- Make fallback behavior explicit and safe by default.
- Preserve deterministic automatic selection.
- Report which provider actually created a service.
- Support provider identifiers used by URI-scheme-oriented domains.
- Remove process-wide mutable registries from downstream crates.
- Keep the core synchronous, explicitly registered, and provider-domain
  agnostic.

## Non-goals

- Runtime registration, replacement, unloading, or hot reload.
- Automatic discovery through `inventory`, `linkme`, dynamic libraries, or
  linker sections.
- Asynchronous provider initialization.
- A general dependency-injection container.
- A generic capability or metadata schema.
- Migration compatibility with `qubit-spi` 0.3.

## Considered Designs

### Incremental cleanup

Keep the mutable registry and existing provider contract, remove `Rc`, and add
a fallback policy. This is the smallest change, but it preserves the ownership
matrix and the coupling between registration, selection, and creation.

### Immutable registry plus policy resolver

Build a provider catalog once, freeze its indexes, and perform creation through
a resolver with an explicit selection and fallback policy. The service
specification chooses the returned handle type. This design matches all known
consumers and is selected.

### General plugin framework

Add dynamic discovery, asynchronous loading, runtime mutation, capabilities,
and lifecycle management. No current consumer needs these features, so this
would introduce policy and lifecycle complexity without evidence.

## Target Architecture

The runtime data flow is:

```text
Provider registrations
        |
        v
ProviderRegistryBuilder<S>
        |
        | build once
        v
ProviderRegistry<S>  ---- metadata/lookup ----> ResolvedProvider<S>
        |
        | shared by value, O(1) clone
        v
ProviderResolver<S> + ProviderSelection + FallbackPolicy
        |
        | create(config)
        v
CreatedService<S::Output> | ResolutionError
```

`ProviderRegistry` is an immutable catalog. `ProviderResolver` owns resolution
policy. Provider implementations own only service construction.

## Core Traits

```rust
pub trait ServiceSpec: 'static {
    type Config: ?Sized;
    type Output;
}

pub trait ServiceProvider<S>: Send + Sync + 'static
where
    S: ServiceSpec,
{
    fn create(
        &self,
        config: &S::Config,
    ) -> Result<S::Output, ProviderError>;
}
```

`ServiceSpec::Output` is a complete, sized handle such as
`Arc<dyn FileSystem>`. `qubit-spi` does not convert among `Box`, `Arc`, and
`Rc`.

The `Debug` supertrait is removed from `ServiceProvider`. Registry debug output
contains descriptors and counts, not provider implementation state.

## Provider Identity

Provider identity and user-configured selectors are distinct concepts.

### ProviderId

`ProviderId` is a strict canonical identifier:

- it is already lowercase ASCII;
- leading or trailing whitespace is rejected, not trimmed;
- it begins and ends with an ASCII alphanumeric character;
- internal ASCII alphanumeric characters and `-`, `_`, `.`, and `+` are
  accepted;
- it is never silently normalized after construction.

This grammar supports values such as `git+ssh`, `vendor.v2`, and
`file-command`.

### ProviderSelector

`ProviderSelector` is parsed at a configuration boundary:

- surrounding whitespace is trimmed;
- ASCII letters are normalized to lowercase;
- the resulting value uses the same character grammar as `ProviderId`.

Descriptors store a canonical `ProviderId` and zero or more selector aliases.
Resolution preserves both the requested selector and canonical provider ID for
diagnostics.

## Provider Descriptor and Registration

Metadata is supplied at registration instead of being returned by a provider:

```rust
let descriptor = ProviderDescriptor::new(ProviderId::new("magika")?)
    .with_aliases([ProviderSelector::parse("ai")?])
    .with_priority(20);

builder.register(descriptor, MagikaMimeDetectorProvider::new(...))?;
```

`ProviderDescriptor` remains intentionally narrow:

- canonical ID;
- aliases;
- default automatic-selection priority.

Domain capabilities and descriptive metadata remain in domain crates until a
second concrete cross-domain requirement exists.

Registration validates descriptor-local alias uniqueness and conflicts against
all earlier registrations. A conflict error includes the conflicting selector
and both canonical provider IDs.

## Builder and Immutable Registry

`ProviderRegistryBuilder<S>` accepts registrations during startup. Its
`build()` operation creates:

- an immutable entry slice;
- a selector-to-entry index;
- an automatic-selection index sorted by descending priority and then
  ascending canonical provider ID.

The built registry contains an `Arc<RegistryInner<S>>`. Cloning a registry is
O(1), and all clones observe the same immutable catalog.

The runtime registry does not expose `register`, `register_shared`, `replace`,
or `unregister`. An application needing a different provider set builds a new
registry explicitly.

Provider registration supports owned and already shared providers without
duplicating the registry API. The exact constructor shape may use a
`ProviderRegistration<S>` value, but the runtime representation is an
`Arc<dyn ServiceProvider<S>>`.

## Lookup and Opaque Provider References

Raw provider trait objects are not returned directly. Lookup returns an opaque
reference that preserves metadata:

```rust
pub struct ResolvedProvider<'a, S>
where
    S: ServiceSpec,
{
    descriptor: &'a ProviderDescriptor,
    provider: &'a dyn ServiceProvider<S>,
}
```

The type exposes the descriptor and a `create` operation. This prevents
callers from losing the canonical identity while retaining explicit named
lookup when a domain does not need fallback selection.

## Selection and Fallback

```rust
pub enum ProviderSelection {
    Auto,
    Named(ProviderSelector),
    Chain(Box<[ProviderSelector]>),
}

pub enum FallbackPolicy {
    OnAbsence,
    OnAnyError,
}
```

Semantics:

| Failure | `OnAbsence` | `OnAnyError` |
| --- | --- | --- |
| Unknown selector | continue | continue |
| Unsupported request/config | continue | continue |
| Provider unavailable | continue | continue |
| Invalid provider configuration | stop | continue |
| Provider initialization failed | stop | continue |

`OnAbsence` is the default because it permits optional providers while not
hiding broken configuration or operational failures. A `Named` selection with
no fallback candidates fails immediately regardless of policy.

`Auto` uses the registry's precomputed deterministic order. A chain deduplicates
aliases that resolve to the same canonical provider so a provider is attempted
at most once.

## Provider Errors

The separate availability probe is removed. Creation is authoritative and may
return:

```rust
#[non_exhaustive]
pub enum ProviderErrorKind {
    Unsupported,
    Unavailable,
    InvalidConfiguration,
    InitializationFailed,
}
```

`ProviderError` is a struct with private fields and accessors for kind, reason,
and optional source error. This avoids a check-then-create race and prevents
downstream exhaustive matching on payload-bearing error variants.

If a future UI needs proactive diagnostics, that capability will be introduced
as a separate optional diagnostic interface. It will not be used as the
resolver's authoritative creation gate.

## Registration and Resolution Errors

The current aggregate registry error is replaced by three layers:

- `RegistrationError`: malformed descriptor, duplicate ID, or alias conflict;
- `ProviderError`: one provider rejected or failed creation;
- `ResolutionError`: selection failed after one or more attempts.

Each public error is a struct with private fields. Its corresponding kind enum
is `#[non_exhaustive]`.

`AttemptFailure` records:

- the requested selector when one exists;
- the canonical provider ID when resolution succeeded;
- failure kind;
- human-readable reason;
- optional source error.

`qubit-spi` does not log provider failures. It returns structured data, and the
application chooses what to log or count.

## Successful Creation

Successful resolution returns provider identity with the service:

```rust
pub struct CreatedService<T> {
    provider_id: ProviderId,
    service: T,
}
```

The type exposes `provider_id()`, `service()`, and `into_service()`. This makes
fallback outcomes observable without forcing logging in the library.

## Internal Module Boundaries

The implementation is split by responsibility:

- `service_spec.rs`: service specification contract;
- `service_provider.rs`: provider construction contract;
- `provider_id.rs`: strict canonical identifiers;
- `provider_selector.rs`: normalized configuration input;
- `provider_descriptor.rs`: immutable registration metadata;
- `provider_registration.rs`: descriptor/provider pair;
- `provider_registry_builder.rs`: validation and index construction;
- `provider_registry.rs`: immutable catalog and lookup;
- `provider_resolver.rs`: attempt execution and fallback policy;
- `provider_selection.rs`: selection values;
- `provider_error.rs`: individual provider failure;
- `registration_error.rs`: builder failure;
- `resolution_error.rs`: attempt aggregation;
- `created_service.rs`: successful provider identity and output.

Small private helpers may remain in their owning module rather than becoming
public abstractions.

## Removed 0.3 API

The 0.4 release removes without compatibility shims:

- `ServiceSpec::Service`;
- `ServiceProvider::descriptor`;
- `ServiceProvider::availability`;
- `ServiceProvider::create_box`, `create_arc`, and `create_rc`;
- `ProviderAvailability`;
- `ProviderCreateError`;
- `ProviderFailure`;
- the aggregate `ProviderRegistryError`;
- mutable registration methods on `ProviderRegistry`;
- all named/auto/selected Box/Arc/Rc creation variants;
- direct raw provider lookup;
- the `Debug` requirement on provider implementations.

## Downstream Migration

### qubit-fs

`FileSystemSpec` uses:

```rust
type Output = Arc<dyn FileSystem>;
```

`FileSystemRegistryBuilder` assembles filesystem providers and produces an
immutable registry. URI schemes are parsed as `ProviderSelector`, including
schemes containing `+` or `.`. Runtime registration methods on `FileSystems`
and `FileSystemRegistry` are removed or moved to their builders.

### qubit-mime

Both `MimeDetectorSpec` and `MediaStreamClassifierSpec` return `Arc` trait
objects. Box creation methods are removed.

The detector and classifier `LazyLock<RwLock<...>>` registries,
`register_default`, lock helpers, lock-poisoning branches, and snapshot clones
are removed. Built-in convenience registries may use immutable `LazyLock`
values, but external providers are assembled explicitly.

`MimeDetectorCore` no longer obtains its classifier registry through hidden
global state. Construction accepts an assembled registry/resolver or the
already created classifier dependency.

### qubit-magika

The Magika provider returns `Arc<dyn MimeDetector>`. The crate exports either a
provider value plus descriptor helper or a complete provider registration.
Applications add that registration while building their MIME registry.

`qubit-mime` does not depend on `qubit-magika`; assembly preserves dependency
direction.

### rs-platform

The platform layer is the natural composition root. As service crates become
implemented, their builders accept already assembled domain registries or
resolvers. No service crate mutates a process-wide SPI registry.

### rs-llmsdk-core

No migration is required. It remains provider-neutral and continues receiving
dependencies such as `Arc<dyn CredentialProvider>`. A future LLM provider SPI
belongs in a provider or assembly crate, not in `rs-llmsdk-core`.

## Testing Strategy

`qubit-spi` contract tests cover:

- strict provider ID validation and selector normalization;
- support for `+` and `.` identifiers;
- descriptor-local and cross-provider conflicts;
- immutable registry cloning and thread sharing;
- deterministic automatic ordering;
- alias deduplication in candidate chains;
- the full fallback-policy matrix;
- preservation of requested selector, canonical ID, and error sources;
- successful creation reporting the winning provider ID;
- service specifications choosing different output handle types;
- custom registry debug output not formatting provider state.

Downstream integration tests cover:

- filesystem resolution from URI schemes;
- MIME detector and classifier built-in assembly;
- Magika registration through explicit application assembly;
- absence of cross-test global registry contamination;
- concurrent creation through cloned immutable registries.

Verification for each affected crate includes tests, all-target/all-feature
Clippy with warnings denied, and rustdoc generation. Downstream crates are
tested against local path versions of the rewritten `qubit-spi`.

## Rollout

The change is released as `qubit-spi` 0.4.0. Migration occurs in dependency
order:

1. implement and verify the new `qubit-spi` core;
2. migrate `qubit-fs`;
3. migrate both `qubit-mime` SPI domains and remove mutable globals;
4. migrate `qubit-magika` and add cross-crate assembly coverage;
5. document the composition-root pattern for `rs-platform`;
6. verify that `rs-llmsdk-core` remains independent.

No deprecated compatibility layer is retained. Keeping both models would
double the public surface and preserve the design ambiguity this release is
intended to remove.

## Accepted Decisions

- Registries are built during startup and immutable afterward.
- Known downstream service specifications use `Arc` outputs.
- Descriptor ownership moves from providers to registrations.
- Provider availability is represented by classified creation errors.
- Default fallback continues only for expected provider absence.
- Mutable process-wide default registries are removed.
- `rs-llmsdk-core` remains independent of `qubit-spi`.
